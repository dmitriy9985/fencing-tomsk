# ФФТО — правила работы с сайтом

## Перед работой

- Перед существенной задачей прочитайте [журнал проекта](docs/PROJECT_JOURNAL.md) и [текущий контекст](docs/PROJECT_CONTEXT.md). Сверьте ветку, SHA, PR и состояние действующего сайта с доступными источниками. Помечайте неподтверждённое отдельно.
- Работайте от проверенного актуального `main` в отдельной ветке или worktree. Первый и второй этапы выпущены на [fencing-tomsk.ru](https://fencing-tomsk.ru/).
- Эксперимент с помощником по соревнованиям приостановлен. Локальная реализация сохранена в `work/news-automation-preparation`, коммит `5443cb0`. Облачная интеграция, мониторинг и публикация требуют отдельного задания.

## Изменения и сохранность

- Сохраняйте архитектуру статического HTML/CSS/JS, оформление, маршруты, админку и существующие данные. Используйте действующие сущности `news`, `competition_events`, `competition_results`, `competition_result_entries` и их связи.
- Для изменений в production, DNS, настройках хостинга, базе и рабочих публикациях требуется разрешение на конкретное действие. Проверяйте, может ли слияние в `main` запустить GitHub Pages.
- Сохраняйте чужие локальные правки, ветки, stash и резервные копии. Перед восстановлением проверяйте исходное состояние и наличие копии.
- Используйте проверенные сведения о спортсменах, результатах и тренерах. Место соревнования само по себе не определяет регион участника. Фото должны иметь подтверждённые права на использование.

## Supabase, MAX и публикация данных

- Сохраняйте RLS и закрытые права записи. Храните секретные ключи, пароли, токены и приватные резервные копии вне frontend, Git, документации и логов.
- Записи, миграции, импорт, seed, отправку уведомлений и проверку изменений тренировок в production выполняйте по отдельному разрешению. Для проверки записи используйте согласованную изолированную среду.
- SQL-файлы в Git описывают исходники миграций. Фактическое состояние схемы и прав проверяйте отдельно.
- При возобновлении автоматизации сохраняйте черновики с `published=false` и ручное подтверждение публикации в существующей админке. Подключение платных API требует согласования.

## Проверки и журнал

- После существенной работы обновите текущий статус и добавьте запись в [хронологию](docs/PROJECT_JOURNAL.md#2-хронология-изменений). Укажите дату по Томску, что изменилось, какие проверки выполнены, состояние production и при необходимости ссылки на PR, коммит или Pages.
- Для документации проверяйте ссылки, отсутствие секретов, сохранение истории и список файлов. Для кода проверяйте затронутую функциональность. Для интерфейса проверяйте настольную и мобильную версии.
- В отчёте различайте проверки исходников, публичные GET-запросы и проверки записи. Указывайте только фактически проверенные сценарии.
