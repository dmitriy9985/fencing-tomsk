### Управление и миграция

На действующем [`fencing-tomsk.ru/admin/`](https://fencing-tomsk.ru/admin/) в уже авторизованном браузере открылся раздел «Новости» и был доступен переход в «Результаты». Обе реализации используют одну публичную конфигурацию проекта Supabase и проверяют `admin_users`, но выпускаются из разных репозиториев. Адрес `admin.fencing-tomsk.ru` из файла CNAME второго репозитория вернул `ERR_CERT_COMMON_NAME_INVALID` в том же браузере. Для текущего релиза раздел «Тренировки» находится в привычной встроенной панели `/admin/#training`. Отдельный репозиторий чист, правок в нём нет. Все действующие администраторы получают одинаковые возможности.

Одна миграция [supabase/training-schedule.sql](../supabase/training-schedule.sql) создаёт `training_slots` с пятью недельными правилами, `training_exceptions` с ключом «слот + исходная дата» и RPC `change_training`. У посетителей есть чтение. Прямые записи запрещены всем клиентским ролям, а функция проверяет `auth.uid()` по существующему `admin_users`. Привилегированная часть размещена в отдельной схеме, которую не следует добавлять в список открытых схем Data API. Публичная RPC является обёрткой с правами вызывающего. Авторизованные администраторы имеют одинаковые права.

Отмена, перенос и возврат сохраняются одной операцией после одного подтверждения. Исходное правило остаётся постоянным. Сервер проверяет даты, прошедшее время, изменение с той же версией и пересечения разных дат одного слота. У разных слотов намеренное пересечение разрешено. При повторной записи старой версии требуется обновить список. Длительность занятия при переносе сохраняется. Возврат восстанавливает исходное время и сохраняет номер версии для защиты от повторного запроса. Причина видна публично, что обозначено у поля. Текст уведомления можно скопировать до и после сохранения и вручную отправить в чат.

#### Резервная копия схемы и данных до миграции

Подставить хост, порт и имя пользователя из **Session pooler** в окне Connect. Пароль базы вводится по запросу Терминала. Команды выполняют чтение. Архив положить вне репозитория и сохранить в закрытом хранилище.

```bash
(
  set -e
  umask 077
  backup_dir="$(mktemp -d "$HOME/ffto-db-before-stage1.XXXXXX")"
  PGSSLMODE=require pg_dump --host='<ХОСТ>' --port='<ПОРТ>' \
    --username='<ПОЛЬЗОВАТЕЛЬ>' --dbname=postgres --password \
    --schema=public --format=custom --file="$backup_dir/public.dump"
  pg_restore --list "$backup_dir/public.dump" > "$backup_dir/contents.txt"
  printf '%s\n' "$backup_dir"
)
```

В `contents.txt` должны быть, среди прочего, записи `TABLE public admin_users` и `TABLE DATA public admin_users`. Этот архив покрывает схему `public`, которую затрагивает выпуск, и её данные. При обычном откате сайта восстанавливать его целиком не нужно. Массовое восстановление поверх рабочей базы может затереть более свежие записи.

#### Проверка базы в SQL Editor сразу после миграции

```sql
begin read only;
set local role anon;
select id, weekdays, starts_at, ends_at from public.training_slots order by starts_at;
select count(*) as exception_count from public.training_exceptions;
select
  has_table_privilege('public.training_slots', 'INSERT, UPDATE, DELETE, TRUNCATE') as can_write_slots,
  has_table_privilege('public.training_exceptions', 'INSERT, UPDATE, DELETE, TRUNCATE') as can_write_exceptions,
  has_function_privilege('public.change_training(text,date,text,integer,date,time,text)', 'EXECUTE') as can_call_change;
reset role;
set local role authenticated;
select
  has_table_privilege('public.training_slots', 'INSERT, UPDATE, DELETE, TRUNCATE') as can_write_slots,
  has_table_privilege('public.training_exceptions', 'INSERT, UPDATE, DELETE, TRUNCATE') as can_write_exceptions,
  has_function_privilege('public.change_training(text,date,text,integer,date,time,text)', 'EXECUTE') as can_call_change;
rollback;
```

Ожидается пять строк, у `monday-evening` время 16:30–18:30, исключений ноль. Для обеих ролей два флага прямой записи должны быть `false`. Последний флаг у `anon` должен быть `false`, у `authenticated` — `true`: право вызвать функцию есть, разрешение изменить расписание функция выдаёт только участнику `admin_users`. До слияния открыть локальный релизный предпросмотр `/training/` с действующей публичной конфигурацией Supabase и убедиться, что данные читаются через Data API, а предупреждение о резервном режиме исчезло. В локальном релизном предпросмотре `/admin/#training` действующий администратор может войти своим аккаунтом, открыть будущую неделю и диалог тренировки и закрыть его без сохранения. Адрес тестовой админки с изолированной БД для проверки действующей авторизации не подходит.

До готовности официального бота текст уведомления копируется и отправляется вручную. После готовности MAX серверную доставку можно привязать к идентификатору занятия и версии изменения. Подключение и очередь не входят в этот этап.

Документация: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [функции базы](https://supabase.com/docs/guides/database/functions), [резервное копирование](https://supabase.com/docs/guides/platform/backups).

### Скорость календаря

Замеры в Яндекс Браузере на одном Mac, по одной принудительной и обычной перезагрузке до и после. Время в таблице отсчитывается от начала навигации. Конец запроса — момент, после которого код читает JSON и обновляет список, а не замер отрисовки пикселей. Браузер мог сохранить DNS и соединения при принудительном обновлении.

| Режим | HTML до / после | CSS до / после | Скрипт страницы до / после | Начало запроса до / после | Конец запроса до / после |
| --- | ---: | ---: | ---: | ---: | ---: |
| Принудительное обновление | 5 / 7 мс | 21 / 31 мс | 23 / 32 мс | 756 / 41 мс | 928 / 434 мс |
| Обычное обновление с кешем | 7 / 8 мс | 15 / 21 мс | 15 / 36 мс | 24 / 37 мс | 206 / 286 мс |

При принудительном обновлении до изменения загрузка supabase-js с jsDelivr шла с 13-й по 746-ю мс. Локальные HTML, CSS и собственный скрипт завершились к 23-й мс. Календарь начинал запрос только после SDK. После изменения отдельная страница календаря читает тот же публичный Data REST API одним GET с теми же полями, сортировкой и фильтром публикации. Даты и лимит на главной обрабатываются прежним кодом. В обеих конфигурациях наблюдался один запрос данных соревнований, без повторной загрузки списка. Служебный CORS-запрос может обрабатываться отдельно от GET. Длительность GET вместе с сетевыми задержками в этих прогонах менялась, поэтому ускорение при тёплом кеше не установлено. При холодной загрузке сокращение ожидания до начала запроса воспроизводится удалением зависимости от CDN.

Python HTTP-сервер отдаёт `Last-Modified`, ответил `304 Not Modified` на условный запрос CSS. В тёплом прогоне CSS и SDK до изменения были взяты из кеша. Публичный статический HTML действующего календаря содержит сразу карточку соревнования за июнь, которую скрипт заменяет актуальными событиями. Локальная страница показывает «Загружаем календарь…» уже из HTML, затем четыре действительных события. Отдельного сопоставимого сетевого профиля хостинга в этих замерах нет. Раннее появление карточки на действующем сайте не свидетельствует о более раннем завершении запроса данных. Источник: [публичный HTML календаря](https://fencing-tomsk.ru/calendar/).

Документация: [Supabase Data REST API](https://supabase.com/docs/guides/api).
