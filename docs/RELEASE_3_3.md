# Выпуск 3.3. Календарь и техническая надёжность

## Админка и просмотр соревнований

Админка открывает «Актуальные»: текущие и будущие записи, включая черновики. Для точной и ориентировочной даты учитывается последний день. Событие с известным только месяцем актуально весь этот месяц и сортируется по его началу. Сравнение выполняется по Томску. «Прошедшие» сортируются по дате окончания от новых к старым. В «Все» сначала идут актуальные, затем прошедшие. Второй фильтр независимо выбирает опубликованные записи или черновики. Исходные даты и статусы в базе сохраняются.

Клик по карточке на `/calendar/` открывает нативное модальное окно. Крестик, Escape, нажатие на затемнение и браузерная кнопка «Назад» закрывают его с возвратом фокуса и позиции списка. «Открыть отдельную страницу» ведёт на прежний адрес `/calendar/event/?id=N`. Оба представления читают один запрос с фильтром публикации и используют одну разметку карточки. Обычные ссылки работают в браузере без поддержки модальных окон. При полном отключении JavaScript списку, как и прежде, недоступны данные Supabase.

В общем списке и анонсе на главной видны дата, название, категория, короткое место и действие «Подробнее». Описание и адрес доступны внутри карточки. Запрос списка получает только данные для анонса. В [карточке первенства СФО №8](https://fencing-tomsk.ru/calendar/event/?id=8) оставлены программа по шпаге, возраст и разряд, время допуска и ссылки на документы. Поле «Первый старт» относится к началу программы первого дня.

## Результаты соревнований

Редактор сохраняет результат, список спортсменов и статус публикации одной транзакцией. Оператор открывает результат через «Изменить», корректирует состав, места и статус, затем нажимает «Сохранить». При конфликте открытая форма сохраняет введённые поля: можно скопировать правки и перенести их в свежую версию записи.

Миграция `20261121113337 results_atomic_save` установлена до публикации редактора из [PR №30](https://github.com/dmitriy9985/fencing-tomsk/pull/30). RPC выполняется с правами вызвавшего и проверяет `admin_users`. Права таблиц, ограничения и RLS совпали до и после. В закрытой резервной копии — 5 результатов, 11 строк участников, ID зависимостей и состояния двух последовательностей. Копия восстановлена на отдельном PostgreSQL, отпечатки совпали с production. После миграции отпечатки и последовательности также совпали. Реальные результаты в проверках записи не использовались.

На изолированных PostgreSQL/PGlite и PostgREST проверены создание, команды, несколько третьих мест, удаление участника, публикация и снятие. Искусственные ошибки внешнего ключа, ограничения места и попытки удалить чужую строку откатили весь запрос. Устаревшая версия дала конфликт. На production авторизованный запрос к заведомо отсутствующему ID вернул `409 RESULT_CHANGED`; анонимный запрос отклонён.

## MAX. Проверка 21 ноября 2026 года

Развёрнутая Edge Function версии 6 активна. Её два файла побайтно совпадают с локальным исходником, использованным в тестах. Из production прочитаны агрегаты: четыре записи `sent`, ноль ожидающих, просроченных и с неизвестным исходом. Минутный Cron за последние сутки показал 1 440 успешных запусков и 0 ошибок. Успех Cron подтверждает запуск SQL-задачи. Доставку конкретного сообщения подтверждает ID MAX в очереди.

| Риск | Что подтверждено и какая защита есть | Нужно ли вмешательство |
| --- | --- | --- |
| Повтор одной ревизии | Уникальность по занятию, дате и ревизии, только один активный отправитель. Перекрывающиеся выборки и запоздалый ответ проверены тестами. При штатной работе вероятность низкая | Изменений нет |
| Пропуск сообщения | После сбоя быстрого запуска запись сохраняется и минутный Cron подбирает очередь. Истёкшие и заменённые ревизии намеренно пропускаются. Долгий сбой может оставить семью без уведомления. Таких случаев в текущем снимке нет | При инциденте сверить очередь и состояние Cron |
| MAX принял POST, подтверждение потеряно | Тайм-аут, некорректный ответ или истёкшая 90-секундная аренда дают `unknown`. Автоповтор мог бы дать дубль, поэтому запись сверяют с MAX вручную. Сценарий покрыт тестом, фактическая частота неизвестна | Сохранить текущую политику |
| Повтор очереди после ограничения | Только HTTP 429 повторяется автоматически. Учитываются Retry-After, возрастающая пауза, максимум пять попыток и актуальность занятия. Это может задержать другие сообщения по тому же чату | Поведение намеренное, тесты прошли |
| Восстановление после сбоя | Тайм-аут быстрого вызова, повтор Cron, старая попытка и восстановление тренировки проверены в изолированной среде. Долгий простой до истечения срока не восстанавливает просроченные сообщения | Изменений нет |
| Зависшие уведомления | Состояния видны в закрытой очереди и логах. Отдельного автоматического оповещения администратора в изученной реализации нет. При инциденте без проверки его можно пропустить | Добавлена инструкция проверки только на чтение |

Для проверки инцидента оператор может запросить состояние и время без чтения текста, получателей и секретов:

```sql
select state, error_code, count(*) as total, min(created_at) as oldest
from ffto_training_private.max_notifications
where state in ('unknown', 'failed', 'expired')
   or (state = 'pending' and next_attempt_at < now() - interval '5 minutes')
   or (state = 'sending' and lease_until < now())
group by state, error_code;
```

Если есть `unknown`, сначала сверить фактическое сообщение в чате и логи. Штатный Cron переводит истёкшую отправку в `unknown`. Заново отправлять сообщение на основании одного статуса нельзя. Для аудита прогнаны 20 SQL-тестов и 7 Deno-тестов со стендом MAX. Production-очередь, Edge Function и Cron не менялись.
